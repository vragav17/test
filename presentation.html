SECTION 01

The problem

Two files. Same title. Nobody can say what is different.

Live board · click the claims

The need

Four people need this answer, for four different reasons

Archive

Is this a version we already hold, or a genuinely new one? Storing the same cut twice is expensive; losing a unique one is worse.

Compliance

A cut was ordered for a territory. Did the supplier actually make it, and only it?

Localisation

Every change to the picture invalidates subtitles and dubs downstream. Which ones moved?

QC

A new master arrived. Is the difference from the last one editorial, or did something break in the transcode?

Today this is a person scrubbing two timelines side by side. It takes hours, it is done under deadline, and it is the first task dropped when the deadline wins.

A tool only helps here if its output can be trusted without re-checking it by hand. That single requirement shapes every design decision in the rest of this deck.

Section 1

The problem

"Two sequences that share an origin and have since diverged."

What is asked

Not "are these different" — which is trivial — but what changed, where, and of what kind.

Why it is hard

One edit shifts everything after it. Position-based comparison collapses at the first cut.

The reframe

Insertions, deletions and substitutions between two related sequences. That is alignment.

SECTION 02

The approach

Turn each film into a string. Then align the strings.

The idea in one table

Genome alignment, with a different alphabet

In genomics

letter a base — A C G T alphabet 4 symbols similarity a substitution matrix algorithm Needleman-Wunsch output match · indel · mutation

In Vidiff

letter a shot — the span between cuts alphabet a 64-bit perceptual hash similarity Hamming distance between hashes algorithm Needleman-Wunsch output equal · delete · insert · replace
A shot is the right unit on both counts. It is editorially meaningful — cuts are exactly where editors work — and a feature has a few thousand of them rather than a few hundred thousand frames.

Live board · the judged component

Needleman-Wunsch, cell by cell

The one interesting optimisation

A sequential-looking recurrence that is not

The left-neighbour term depends on the cell beside it:

H[i][j] = max(…, H[i][j-1] + gap)

That looks inherently serial. With a linear gap penalty it is a running maximum in disguise.

Substitute G[j] = H[i][j] − j·gap:

G[j] = max(best[j] − j·gap, G[j-1]) = np.maximum.accumulate(…)

Each row becomes three vector operations instead of an inner Python loop.

A feature-length pair aligns in seconds, on a laptop, in pure numpy. No bioinformatics library, no heuristic, and no model anywhere near it — align.py contains zero references to one, verifiable with a single grep.

Section 2

The approach

"Shots are letters. Hamming distance is similarity. The rest is arithmetic."

Mental model

Two edits of a film are two spellings of the same sentence. Alignment finds where the spellings diverge.

Technically

Global alignment over 64-bit perceptual hashes, scored +2 / 0 / −1 with a linear −1 gap, vectorised per row.

Why it matters

It returns the provably optimal alignment, not a good-enough one — and the same one every time.

SECTION 03

The second signal

A re-dub changes nothing on screen.

Live board · switch the audio signal off

Six shots that look identical

A deliberate boundary

Audio annotates the timeline. It never scores it.

# the scoring function sees picture only def score_matrix(a_bits, b_bits): d = hamming_matrix(a_bits, b_bits) s = np.full(d.shape, MISMATCH_SCORE) s[d <= WEAK_MAX_DISTANCE] = WEAK_SCORE s[d <= MATCH_MAX_DISTANCE] = MATCH_SCORE return s
# …and afterwards, over aligned pairs only if op.type == "equal" and ahash_distance > 16: op.type = "audio_changed"

A second pass over what the alignment already matched — not a second term inside it.

Why the separation. An audio term inside the scoring function would make the alignment's behaviour a matter of tuning two weights against each other. The alignment is the part that has to be defensible, so nothing else is allowed to move it. A corrupt audio track can annotate wrongly; it can never corrupt the structure.

SECTION 04

The pipeline

Eight stages, two parallel lanes, one merge.

Live board · click any stage

What each stage actually does

The stage that earns its keep

One normalised 480p file, and everything downstream gets easier

Cheap to read

Every later stage decodes a small H.264 file instead of a 200 GB master. Shot detection and hashing stop being I/O-bound.

Comparable by construction

Same resolution, same colour space, all audio tracks merged. Two versions are made alike before anything measures them.

Cached and reused

Build it once per file. Compare that file against anything else later and the expensive half is already done.

One deliberate exception. The technical probe reads the source, never the proxy. The proxy is 8-bit BT.709 by definition, so probing it would report every HDR master on earth as SDR.

Live board · switch the model off

The model writes the sentence. It never finds the change.

Three reasons the boundary sits exactly there

Detection is arithmetic. Description is prose.

Reproducible

The same two files give the same regions — run to run, machine to machine, today and next year. No sampling, no temperature, no drift.

Auditable

A disputed result traces to a Hamming distance and a scoring rule you can read in twenty lines. Not to a token that happened to be sampled.

Honest about failure

A wrong description is obvious beside its own thumbnails. A wrong timecode would be undetectable — so the model is never allowed to produce one.

The build order made this concrete: stages 0–5 and 7 had to work with the model disabled before stage 6 was written at all.

SECTION 05

The proof of concept

The pipeline, as a workflow application.

Pick · watch · read

Vidiff

Pick

A built-in file browser walks the local disk. No upload, no copy, nothing leaves the machine. Labels, thresholds and a switch for the descriptions.

Watch

The two lanes light up in parallel and merge at alignment. Server-sent events stream every stage transition and log line live, with per-stage timings.

Read

Changes group by kind rather than arriving as a flat list. Each region shows both sides' thumbnails, and each column carries its own audio.

backend FastAPI + uvicorn, bound to 127.0.0.1 only frontend React 19 + Vite + TypeScript progress SSE, 200 ms poll — no queue to deadlock parallel 2 workers, one per version lane history every job kept under .cache/jobs/, re-openable
Hearing the difference. An audio_changed region is a claim about sound, and the only real way to check it is to listen. Both versions get a play button in their own column, side by side; only one plays at a time.

Clips are cut on demand, from the original where it is still on disk: one lossy generation instead of two, and every audio track rather than whichever one ffmpeg would have picked.

SECTION 06

What real formats taught us

Three bugs that only genuine delivery files could find.

Live board · bug 01 · click the tracks

Five of six audio tracks silently vanished

Live board · bug 02 · toggle the tone-map

Every shot faked a replace

Bug 03 · the subtle one

A fixed pipeline, still producing broken output

The trap

Both fixes above change how a proxy is built. A proxy cached from before the fix is still a perfectly valid file, so it was reused — and the bug survived its own fix, invisibly, on every machine that had ever run the tool.

The fix

PROXY_PIPELINE_VERSION is part of the cache key. Bump it and every stale proxy is rebuilt. The general lesson: a cache keyed on inputs alone is wrong the moment the transform can change.

And one that cut the other way. The leading theory for the audio problem was double-lossy encoding. Measured, it cost 0.4 dB — nothing. It was not the cause, and saying so was more useful than claiming the credit.

This is the habit the whole project runs on: form the hypothesis, measure it, and report the measurement even when it contradicts you.

SECTION 07

Does it work?

Eight acceptance checks against recorded ground truth.

Live board · run the suite

The pipeline is never shown the answer

Stated plainly

What this proof of concept does not do

Colour is invisible

phash is greyscale by construction. A re-grade or a colourisation measures 0/64. The tool reports "no change" and is confidently wrong.

Two versions only

No fingerprint database, no library-wide dedup, no three-way compare. Deliberately out of scope for a proof of concept.

Synthetic fixtures

Every fixture is generated, MXF and HDR included. Real footage — dissolves, handheld, fast cutting — has not been measured.

One frame per shot

A change inside a long take, away from its midpoint, can be missed entirely. Shot detection runs at a single fixed threshold.

None of these is a surprise or a defect — they are the consequences of choosing a working end-to-end path over completeness. They are written down because a tool that hides its blind spots is more dangerous than one that has none.
